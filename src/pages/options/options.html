请求统计

ⓘ这些数字怎么数出来的

只统计命中了你的规则的请求；其余请求本就该直连，不计入。

成功的判定是 HTTP 状态码小于 400。

浏览器缓存命中的请求单独一格：它一个字节都没出去，不算一次代理往返。 所以翻回去重看同一页漫画时，总量不会跟着涨。

耗时给的是分位数而不只是平均值：「中位数」是一般要等多久， 「慢的那一成」（p90）是最慢那 10% 要等多久。平均值会被少数十几秒的长尾拉高， 也会被大量缓存读拉低，两头一抵就变成谁都没经历过的数。

「按规则送去代理」是意图，「对端确认是代理」才是结果 —— 后者看响应从哪个地址回来的，落在你某个节点上才算走通了。连接层就失败的请求 进不了后者。

重试与兜底

ⓘ为什么开了重试之后成功率会变低

重发是一次全新的请求，会被如实计进上面「请求统计」的总量里。 所以开启重试之后总量变大、成功率变低是正常的 —— 用「重试」这一格来对账。

「重试救回」是重发之后真的加载成功了，不是估算。「兜底接管」是轮询节点全试过之后 切到兜底代理的次数；「冷却期跳过」是本该切、但该图源刚用过兜底而没切的次数。

「结果未知」是重发出去了，但那张图已经被页面换掉或者页面导航走了 —— 浏览器不会再派发任何事件，这次重发的结局永远不会有人回报。它既不算救回也不算失败。

「页面没捕获」是网络层确实失败了，但页面侧收不到通知：只有 DOM 里的 <img> 会派发可捕获的 error。这一格不为零说明重试机制对那些图 整体无效，调重试次数不会有任何改变。

节点使用分布

ⓘ这张表为什么可能认不出节点

归因靠请求的对端 IP —— 走代理时对端就是代理本身。只有 IP，没有端口， 所以多个节点共用同一个地址（只有端口不同）时无法区分。

这类请求计入「无法归因」，不会硬塞给某个节点。节点写成域名时要先测速一次才认得出。

Easy Proxies 自动拉取

ⓘ自动拉取怎么工作

从 easy_proxies 管理接口按最近探测延迟拉取最优节点（可用且未拉黑）， 填入节点列表。每次同步只替换由本功能管理的节点，手写节点不受影响； 可用节点不足时按实际数量填入。

填写「本地标签服务地址」后，每次同步会先拉取 easy_proxies， 再调用本地标签工具的 /api/convert，把同 IP 不同端口 转换成唯一的 127.0.0.x 节点并自动填回，让统计面板 能按端口归因。使用前需先启动本地工具（见 tools/label-proxy 的 README）。

管理地址没写协议时自动补 http://；填了密码会先调用 /api/auth 登录。代理主机名取管理地址的主机名。

规则之外的流量

ⓘ为什么这里需要你填一次

浏览器只有一份代理设置。本扩展一生效就会整份接管它 —— 包括你原来的「使用系统代理设置」。于是没命中规则的请求会拿到真·直连， 而不是「照旧走你本机的代理客户端」。

如果你平时靠本机客户端（Clash、sing-box、v2rayN 等）或系统代理上网， 这会表现为：图片站一切正常，其余网站全部 ERR_CONNECTION_TIMED_OUT。扩展这边不会报任何错 —— 它确实按你写的规则做了它该做的事。

填上你客户端的代理端口（多数是混合端口，例如 http://127.0.0.1:7897）， 规则之外的流量就会照旧从那里出去，与没装本扩展时一样。

扩展读不到系统代理的地址，所以只能由你填一次：Chrome 出于隐私 只告诉扩展「在用系统代理」，不说它指向哪里。

127.0.0.1、192.168.* 等本地与私有地址始终直连， 不受这里影响；总开关关闭时整份分流设置都不生效，浏览器会回到它自己的代理设置。

重试与兜底

ⓘ重试是怎么做到的，能救回哪些图

代理连不上时，扩展让页面把这张图重新请求一次。新请求会落到轮询里的 下一个节点，刚失败的那个已被浏览器自己排除。一个请求始终只挂一个代理， 所以轮询不会因为重试而变得不均匀。

只有 <img> 救得回来。CSS 背景图、canvas、以及页面自己用脚本取图再塞进 <img> 的阅读器不派发可捕获的错误事件，这类图片救不到。要覆盖 fetch / XHR / 预加载图，见下面的「深度重试站点」。

图源返回 404 / 5xx 时不重试：换个代理拿到的还是同一个结果。

慢图看门狗盯的是“慢但没失败”的请求：测速只能量出 「连上代理要多久」，量不出「一张图多久才下得完」；而且节点很多时串行测速 本身就慢。看门狗直接给真实图片请求计时，超过阈值还没 `load` 就主动换节点。 它只覆盖 DOM 里的 <img>，CSS 背景图 / canvas 救不回来。

兜底代理是一个普通的 HTTP/HTTPS 代理，填「地址:端口」就行。它独立于 节点列表：不参与轮询、不测速、不会被自动禁用。轮询节点全试过仍然失败时， 扩展把这个图源临时指向它，然后让页面再发一次。

它是按「图源」生效的，不是按单张图。浏览器只把「协议+域名」交给分流 脚本（路径和查询串被剥掉了），所以没法只让某一张图换代理。兜底触发后的 12 秒内，这个图源的所有请求都会走兜底代理；随后进入 30 秒冷却期， 冷却期内用尽的图直接裂掉。冷却是刻意的 —— 否则轮询池持续失败时，整个图源会 长期只走兜底代理那一个 IP，而这正是本扩展存在意义的反面。

深度重试站点

ⓘ它做什么、代价是什么

普通重试只救得回页面 DOM 里的 <img>。阅读器常用 new Image() 预加载大图、或用 fetch / XHR 取图和调接口 —— 那些请求裂了，扩展收不到任何通知，调高重试次数也没用。

在这里填上的站点会被额外注入一小段代码，包住这三个入口，让它们的网络失败也能 换个节点重发一次。只重发 GET / HEAD —— 发评论、点收藏这类请求 一律原样报错，不会被重复提交。

代价必须说清：这段代码跑在页面自己的 JS 环境里（主世界）， 理论上可能与站点自己的封装冲突。所以它只装在你填的站点上， 没填的站点一个字节都不会被注入。填之前请确认你信任这个站点，出问题就把它删掉。

填法：直接写域名（nhentai.net，自动覆盖子域名）， 或写完整匹配范围（https://noymanga.com/read/*）收窄到具体路径。 一行一条。

ⓘ它记什么、和「最近活动」有什么区别

「最近活动」是给你看的：一句话说清刚才那张图走了哪个节点。这里记的是给开发者看的 内部状态 —— PAC 编译与注入的结果、每个请求的归因过程、重试判定的全部入参、 页面侧到底重发了没有。两路日志互不影响，这里的开关不会动那一路。

导出时每个环节各成一个文件（pac / request / retry / content 等）。跨环节对时间线要用合并文件。

默认关闭，关着时不产生任何开销。开启后记录在会话存储里， 关掉开关或重启浏览器都会清空 —— 所以要先开开关，再重现问题。

分流脚本（PAC）内部发生的事记不到：它跑在浏览器的沙箱里，没有回传通道。 「这个请求选了哪个节点」只能看 request 里的对端 IP。
