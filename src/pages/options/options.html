请求统计

ⓘ这些数字怎么数出来的

只统计命中了你的规则的请求；其余请求本就该直连，不计入。

成功的判定是 HTTP 状态码小于 400。

浏览器缓存命中的请求单独一格：它一个字节都没出去，不算一次代理往返。 所以翻回去重看同一页漫画时，总量不会跟着涨。

耗时给的是分位数而不只是平均值：「中位数」是一般要等多久， 「慢的那一成」（p90）是最慢那 10% 要等多久。平均值会被少数十几秒的长尾拉高， 也会被大量缓存读拉低，两头一抵就变成谁都没经历过的数。

「按规则送去代理」是意图，「对端确认是代理」才是结果 —— 后者看响应从哪个地址回来的，落在你某个节点上才算走通了。连接层就失败的请求 进不了后者。

重试与兜底

ⓘ为什么开了重试之后成功率会变低

重发是一次全新的请求，会被如实计进上面「请求统计」的总量里。 所以开启重试之后总量变大、成功率变低是正常的 —— 用「重试」这一格来对账。

「重试救回」是重发之后真的加载成功了，不是估算。「兜底接管」是轮询节点全试过之后 改用兜底图片代理的次数。

「结果未知」是重发出去了，但那张图已经被页面换掉或者页面导航走了 —— 浏览器不会再派发任何事件，这次重发的结局永远不会有人回报。它既不算救回也不算失败。

「页面没捕获」是网络层确实失败了，但页面侧收不到通知：只有 DOM 里的 <img> 会派发可捕获的 error。这一格不为零说明重试机制对那些图 整体无效，调重试次数不会有任何改变。

节点使用分布

ⓘ这张表为什么可能认不出节点

归因靠请求的对端 IP —— 走代理时对端就是代理本身。只有 IP，没有端口， 所以多个节点共用同一个地址（只有端口不同）时无法区分。

这类请求计入「无法归因」，不会硬塞给某个节点。节点写成域名时要先测速一次才认得出。

重试与兜底

ⓘ重试是怎么做到的，能救回哪些图

代理连不上时，扩展让页面把这张图重新请求一次。新请求会落到轮询里的 下一个节点，刚失败的那个已被浏览器自己排除。一个请求始终只挂一个代理， 所以轮询不会因为重试而变得不均匀。

只有 <img> 救得回来。CSS 背景图、canvas、以及页面自己用脚本取图再塞进 <img> 的阅读器不派发可捕获的错误事件，这类图片救不到。

图源返回 404 / 5xx 时不重试：换个代理拿到的还是同一个结果。

兜底图片代理是按地址取图的服务（如 wsrv.nl、imgproxy、自建 Worker）， 用 {url} 放原图地址（已编码），要求不编码的服务用 {raw}。 它会拿到你的图片地址，用公共服务等于交给第三方。

测速与健康检查

ⓘ测速地址该填什么

应当是一个返回极小响应且允许跨域的端点，例如只回 204 的探测地址。 下载一张大图当测速目标，量到的是带宽而不是延迟。

测速请求会被强制路由到被测节点，所以一次测速就等价于验证了这条节点的 CONNECT 通路。

ⓘ它记什么、和「最近活动」有什么区别

「最近活动」是给你看的：一句话说清刚才那张图走了哪个节点。这里记的是给开发者看的 内部状态 —— PAC 编译与注入的结果、每个请求的归因过程、重试判定的全部入参、 页面侧到底重发了没有。两路日志互不影响，这里的开关不会动那一路。

导出时每个环节各成一个文件（pac / request / retry / content 等）。跨环节对时间线要用合并文件。

默认关闭，关着时不产生任何开销。开启后记录在会话存储里， 关掉开关或重启浏览器都会清空 —— 所以要先开开关，再重现问题。

分流脚本（PAC）内部发生的事记不到：它跑在浏览器的沙箱里，没有回传通道。 「这个请求选了哪个节点」只能看 request 里的对端 IP。
