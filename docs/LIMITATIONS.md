# 技术限制

本文档说明本扩展**做不到什么**，以及为什么。这些都是浏览器扩展平台或网络栈的固有约束，
不是可以靠多写代码绕过的缺陷。

---

## 1. 只支持 HTTP / HTTPS 代理

**结论：可用的代理类型只有 `http://` 与 `https://`。**

浏览器扩展改变请求出口的唯一手段是 `chrome.proxy` API 的 PAC 脚本模式。PAC 脚本的
`FindProxyForURL()` 只能返回浏览器网络栈认识的少数几个关键字，而本项目只登记了
`PROXY`（HTTP 代理）与 `HTTPS`（HTTPS 代理）两种。

其他代理类型一律不受支持，粘贴时会被逐条提示并忽略：

| 类型 | 为什么不支持 |
|---|---|
| SOCKS4 / SOCKS5 | 已从支持范围中移除；且 Chromium 网络栈本身不支持 SOCKS 的用户名密码认证，带认证的节点无法可靠工作 |
| VLESS / VMess | 需要在原始 TCP 之上做自定义握手与加密。扩展拿不到原始 socket（`chrome.sockets.*` 只存在于已废弃的 Chrome Apps） |
| Hysteria2 / TUIC | 基于 QUIC，还带自定义拥塞控制。扩展既不能收发 UDP，也无法接入 QUIC 栈 |
| Trojan | 需要在 TLS 之上直接承载原始 TCP 流量 |
| Shadowsocks / SSR | 需要原始 TCP + 自定义流加密 |

**纯 JavaScript 无法实现上述任何一种协议的隧道**：扩展环境既没有原始 TCP/UDP socket，
也无法自行完成 TLS 握手并验证证书链。任何声称能在浏览器扩展内直接跑这些协议的方案，
实际上都依赖一个本地客户端在旁边转发。

**如果你手上只有这些类型的节点**，可行做法是在本机运行一个客户端（sing-box、Clash、
v2rayN 等），让它开一个**本地 HTTP 混合入口**，然后把那个本地地址（如
`http://127.0.0.1:7890`）当成普通 HTTP 代理加进本扩展。但要注意：这样只有一个出口，
达不到「多 IP 分流」的目的 —— 除非本地客户端开多个端口、每个端口对应不同的上游出口，
再把这些端口逐个加进来。这属于用户自行搭建的环境，本扩展不再提供相关配置生成能力。

---

## 2. HTTPS 目标需要代理支持 CONNECT

漫画图片绝大多数是 `https://`。浏览器经 HTTP 代理访问 HTTPS 资源时，必须先向代理发
`CONNECT` 建立隧道。如果代理只允许明文 HTTP 转发、或禁止 `CONNECT` 到 443 以外的端口，
节点会表现为「看起来在线，但图片全失败」。

**本扩展的应对**：默认测速地址是 `https://` 开头，且测速请求会被**强制**路由到目标节点
（见第 12 节），因此一次测速就等价于验证了这条 CONNECT 通路。测速能过、图片却失败，
通常是目标站点或规则的问题，不是代理不支持 CONNECT。

---

## 3. 代理凭据不能写进 PAC

PAC 语法里没有携带账号密码的位置（`PROXY user:pass@host:port` **不是**合法写法）。

**本扩展的应对**：用 `chrome.webRequest.onAuthRequired`（需要 `webRequestAuthProvider`
权限）在浏览器要求认证时按 `主机:端口` 匹配到对应节点并自动应答，用户不会看到认证弹框。
凭据只存在 `chrome.storage.local`，不会出现在 PAC 脚本里 —— 这一点有单元测试守着。

同一请求第二次要求认证时扩展会停止应答（说明凭据不对），交还给浏览器弹框，避免无限重试。

---

## 4. HTTP/2 连接复用会降低分流粒度

即使 PAC 为每个请求返回不同节点，浏览器仍可能把多个请求塞进**已经建立**的连接里 ——
HTTP/2 的多路复用就是为此设计的。结果是「几十张图片只用到了少数几个节点」。

这是网络栈行为，PAC 层面无法否决。

**缓解办法**
- 节点数 ≥ 4，池子越大越容易被摊开
- 「每几个请求换一次节点」保持默认值 1
- 图源分布在多个域名时效果更好（不同域名不共享连接）

**如何确认分流真的生效**：先看统计里的「真的走了代理」是不是非零、「命中但直连」是不是 0；
再看状态页「最近活动」里的**对端 IP**。同一批图片出现多个不同 IP 就是硬证据；
全是同一个 IP 说明连接被复用了。

---

## 5. Chromium 自带「坏代理」列表

连接失败的代理会被浏览器自己拉黑约 5 分钟，期间即使 PAC 返回它也会被跳过。

这会与本扩展的自动禁用叠加，表现为「刚失败的节点在扩展里还显示可用，但实际没被使用」。
属于双重保护，不是缺陷。等待几分钟或手动点「重置」即可。

**重试功能反过来依赖它**（见第 14 节）：重发一张图时，「不要再落到刚失败的那个代理上」
这件事就是靠这份列表保证的，扩展自己不维护「本次请求已试过哪些节点」的状态。
副作用是：把「每几个请求换节点」设得比较大时（例如 10），重发很可能仍然命中同一个节点，
此时能否换掉完全取决于这份列表 —— 想让重试更可靠，把它保持在默认值 1。

---

## 6. 浏览器代理设置是独占资源

`chrome.proxy` 一次只能由一个扩展控制。若另一个代理类扩展先占了，或企业策略强制了代理，
本扩展的设置会被忽略。

**本扩展的应对**：每次注入后读取 `levelOfControl`，不是 `controlled_by_this_extension`
时在设置页和状态页顶部显示红色告警，而不是假装成功。

---

## 7. 测速地址必须允许跨域

测速请求由扩展的 Service Worker 用 `fetch` 发出，会受 CORS 约束。默认地址
`https://cp.cloudflare.com/generate_204` 返回 204 且允许跨域，适合做探针。

换成不返回跨域响应头的地址，测速会统一失败并提示「探测地址不支持跨域」。此时换回默认地址即可。

---

## 8. PAC 失败时的行为

注入 PAC 时使用 `mandatory: false`。含义是：PAC 脚本执行出错时浏览器**直连**，而不是断网。

同时生成的 PAC 顶层包着 `try/catch`，任何内部异常都返回 `DIRECT`。这是刻意选择的安全默认值 ——
一条手误的正则最坏结果是「不走代理」，绝不会是「整个浏览器上不了网」。

用户输入的正则在写入配置前就会被 `new RegExp()` 预校验，非法的直接拒绝保存；
历史配置里的非法正则在加载时被丢弃，并在设置页标红说明。

---

## 9. Service Worker 会休眠

MV3 的后台是 Service Worker，空闲时会被回收。因此：
- 定时测速用 `chrome.alarms`（能唤醒 SW），不用 `setInterval`
- 轮询计数器活在 PAC 脚本自己的作用域里，不依赖 SW 常驻
- 日志写进 `chrome.storage.session`，统计写进 `chrome.storage.local`，SW 被唤醒后都能接上

`chrome.alarms` 的最小周期是 1 分钟，所以定时测速间隔填小于 1 的值会被提升到 1。

**统计与日志的落盘是节流的**（决策 D15）：计数发生在 `webRequest.onCompleted` 上，一个漫画页
能打出几百个图片请求，每次都落盘就是几百次写操作。所以统计攒够 5 秒或 50 次改动才写一次，
日志攒 3 秒写一次。代价是 SW 恰好在窗口内被回收时，最多丢一个窗口的计数与日志。
这是有意的取舍：统计不是账本，用这点精度换掉几百倍的写放大是划算的。

---

## 10. 历史配置中的不支持节点

早期版本曾计划支持 SOCKS 与若干高级协议。如果你的配置里还留着这类节点：

- 它们**不会**参与分流（`pacToken()` 对它们返回 `null`，因此进不了 PAC 节点池）
- 加载时后台日志会给出明确告警
- 设置页会把它们标红为「不支持」，启用开关被禁用
- 可点「清除不支持的节点」一键删除

不会出现「静默参与分流」的情况 —— 这一点由单元测试覆盖。

## 11. PAC 脚本只能是纯 ASCII

`chrome.proxy` 对 `pacScript.data` 有一条无条件的 ASCII 校验。出现任何一个非 ASCII 字节，
`chrome.proxy.settings.set()` 就**整体**抛错：

```
'pacScript.data' supports only ASCII code(encode URLs in Punycode format).
```

注意是整体失败 —— 不是那个字符被忽略，而是一条 PAC 都注入不进去。而注入失败之后浏览器
照旧直连，图片照样能加载，所以这个故障的表现是「扩展安静地什么都没做」，只在活动日志里
留下一行错误。这类故障比崩溃难查得多。

本扩展的应对（决策 D13）：

- 生成的 PAC 里**注释只写英文**。生成器源码里的中文注释不会跟着产物走。
- 用户配置（规则内容、绕过列表）经 `asciiJson()` 注入，所有非 ASCII 字符转成 `\uXXXX`。
  这是 JSON 与 JS 都认的转义，**语义完全不变**，只是换了一种写法。顺带也转义了
  U+2028 / U+2029 —— 这两个字符在 JS 里算换行符，裸着出现在字符串里会把脚本从中间截断。
- 注入前还有一道 `isAscii()` 断言。真万一漏了，用户看到的是一句中文说明加导出配置的建议，
  而不是 Chrome 那句英文原文。

### 中文域名（IDN）

浏览器交给 `FindProxyForURL(url, host)` 的 `host` **已经是 Punycode 形式**：`漫画.com`
到那里是 `xn--qex62k.com`。所以：

| 位置 | 处理 |
|---|---|
| 节点主机名 | 自动转 Punycode（`pacToken()`） |
| **域名**类型的规则 | 自动转 Punycode，且 JS 侧的规则测试器用同一个函数，两边结论一致 |
| 绕过列表 | 自动转 Punycode，通配符保留（`*.漫画.com` → `*.xn--qex62k.com`） |
| 精确 / 前缀 / 通配符 / 正则类型的规则 | **不转换**，改为在设置页给出警告 |

最后一行是刻意的：这四种类型的内容是整条 URL 的模式，无法可靠判断哪一段是域名，
自动改写会出错。这类规则原样保留（不再报错），但会在「规则」分区显示提示，说明它
可能永远命中不了，并建议改用「域名」类型。**静默失效比明确的警告更难排查。**

补充一点：浏览器交给 PAC 的 URL 里，**路径**中的非 ASCII 字符已被规范化成 UTF-8
百分号编码（`/漫画/` → `/%E6%BC%AB%E7%94%BB/`）。所以「在正则里写中文路径」不是
「可能不命中」，而是**确定不命中**。

## 12. PAC 拿不到 HTTPS 请求的路径与查询串

**这是本扩展最容易踩、也最难自查的一条。**

Chromium 在调用 `FindProxyForURL(url, host)` 之前会先净化 URL
（`net/proxy_resolution/proxy_resolution_service.cc` 里的 `SanitizeUrl`）：

| 方案 | PAC 实际收到的东西 |
|---|---|
| `http://` | 去掉凭据与 `#fragment`，**路径与查询串保留** |
| `https://` / `wss://` | 去掉凭据与 `#fragment`，**路径与查询串一并清空** |

也就是说，页面请求 `https://cdn.manga.com/img/001.jpg?v=2` 时，分流脚本看到的只有

```
https://cdn.manga.com/
```

这是 Chromium 52 起的隐私措施。曾经可以用 `PacHttpsUrlStrippingEnabled` 策略或
`--unsafe-pac-url` 关掉，但该策略在 Chrome 74 就被移除了，**现在无法关闭**。

### 为什么这个故障特别难查

规则不会报错，只是永远不命中；不命中就是直连；直连之后图片照样加载。于是：

- 设置页的规则测试器说「命中」（它拿的是完整 URL）
- 「最近活动」里有一堆 `request` 记录（`webRequest` 也拿得到完整 URL）
- 统计说「走代理的请求 277 次、成功率 100%」
- 而**代理服务商后台一条连接都没有，一点流量都没用**

1.2.0 及更早的版本正是如此：README 教用户优先启用的那条预设规则是
`\.(jpe?g|png|webp)(\?.*)?$`，它对 HTTPS 图片永远命中不了。更糟的是测速也用同样的
机制传递节点标记（`?__pp_node=<id>`），标记同样到不了 PAC，于是每次测速实际走的是直连，
却被记成「该节点延迟 xx ms」——**节点永远显示正常，代理却从未被使用过。**

### 各类型规则在 HTTPS 下的实际行为

| 类型 | HTTPS 下 | 说明 |
|---|---|---|
| **域名** | 完全按预期 | 只看主机名，天然安全。**推荐优先使用这一种** |
| 前缀 / 精确 | 退化成「同源」 | `https://cdn.m.com/img/` → 整个 `https://cdn.m.com/` |
| 通配 | 退化成「域名通配」 | `https://*.m.com/img/*.jpg` → 整个 `https://*.m.com/` |
| 正则 | 只能约束域名部分 | `^https?://(img\|cdn)\d*\.` 有效；`\.jpg$` 无效 |

退化意味着**范围被放宽**：原本只想代理 `/img/` 下的请求，HTTPS 下会代理该域名的全部请求。
这是刻意的取舍 —— 放宽可以接受，悄悄失效不行。`http://` 请求不受影响，路径照旧精确匹配。

### 本扩展的应对（决策 D16）

1. **PAC 里每条 URL 形态的规则都带一份退化形式**，由 `rule-matcher.sanitizedScope()` 生成，
   只在 URL 被净化过时才启用。
2. **JS 侧新增 `matchPacUrl()`**，先用 `pac-url.pacUrl()` 复刻浏览器的净化行为再匹配。
   「这个请求会不会走代理」只由它回答；原来的 `matchUrl()` 现在只代表「用户的意图」。
3. **统计里单列「命中但直连」**（`requests.blind`）。两种匹配的差值就是这一项，
   它不为零就说明有规则写成了 PAC 判定不了的形态 —— 这是最该先查的信号。
   活动日志也会为每条这样的规则给出一次说明（只一次，不刷屏）。
4. **规则列表逐条提示**：能退化的说明「实际范围被放宽到 X」，退化不了的说明「对 HTTPS 不生效」。
5. **规则测试器同时给出两个结论**：完整 URL 命中什么、浏览器实际交出去的 URL 命中什么。
6. **测速改成串行定向**：为目标节点单独生成一份「把测速地址所在源钉到该节点」的 PAC，
   测完恢复。一份 PAC 只能定向一个节点，所以并发没了 —— 一个能骗人的并发测速比慢一点的
   诚实测速糟糕得多。定向失败（控制权被占、协议不支持、测速地址非法）时测速**判失败**，
   绝不报告一个直连的延迟。
7. **预设规则全部换成 HTTPS 下真正有效的形态**，依赖扩展名的那条改成只匹配 `http://`
   并在名字里写明。

测试层面，`tests/helpers/pac-sandbox.js` 里的 `browserUrl()` 负责模拟浏览器的净化，
所有 PAC 断言都必须经它走一遍。**旧测试直接把完整 URL 喂给 `FindProxyForURL`，
于是 271 个测试全绿而扩展一个请求都没代理出去** —— 这是这次修复最重要的一课。

## 13. 归因只能看到对端 IP，看不到端口

`webRequest.onCompleted` 给出的 `details.ip` 是这次连接的**对端 IP**。走代理时对端就是
代理服务器，所以这个字段既能证明「请求真的从代理回来了」，也是唯一能用来反查节点的线索。

问题是：**它只有 IP，没有端口。**

而「一台代理机开几十个端口、每个端口一个上游出口」是最常见的部署形态。这种配置下几十个
节点的 `host` 完全相同，只有端口不同 —— 于是「是哪个节点在干活」这个问题**无解**。

1.2.1 曾用 `nodes.find(n => n.host === ip)` 取第一个匹配，后果是把全部用量记到了列表里
第一个节点上。19 个同 IP 节点的面板长这样：

```
http-10.0.0.3:24026    94 次   100%
http-10.0.0.3:24000     0 次     0%
...（其余 17 个全是 0）
```

看起来像「轮询坏了，只有一个节点在工作」，实际上 19 个端口都在正常轮询 —— 是归因在编数字。

**本扩展的应对（决策 D18）**：

| 情况 | 处理 |
|---|---|
| 对端 IP 只匹配一个节点 | 精确归因到它 |
| 对端 IP 匹配多个节点（共用地址） | **不猜**，计入「无法归因」，并在面板上说明共用了哪个地址、有几个节点 |
| 对端 IP 不属于任何节点 / 没有 IP | 计入「无法归因」 |

同时新增一项「**对端确认是代理**」（`requests.viaNodeIp`）：对端 IP 属于你某个节点的次数。
它回答的是「真的从代理回来了吗」，而不是「是哪个节点」—— 共用地址时前者照样可以确定。
这一项才是分流生效的硬证据。

**想确认轮询是否均匀**：看代理服务商后台的**分端口流量**。扩展做不到，浏览器没给这个信息。

## 14. 重试只救得回 `<img>`

失败的图片能不能被换个代理重发一次，取决于浏览器有没有派发一个**可捕获的 `error` 事件**。

| 图片是怎么来的 | 能救回吗 | 原因 |
|---|---|---|
| `<img src>` / `<img srcset>` | ✅ | 在 `document` 的捕获阶段收得到 `error` |
| `<picture>` + `<source>` | ✅ | 全部源都失败时 `<img>` 会派发 `error` |
| CSS `background-image` | ❌ | 加载失败不派发任何脚本可见的事件 |
| `<canvas>` 里画的图 | ❌ | 同上 |
| 页面 JS 用 `fetch` / `XHR` 取 blob 再塞给 `<img>` | ❌ | 失败发生在页面自己的 Promise 里，扩展看不到 |

最后一类要补上就得向**主世界**注入代码去包住 `window.fetch` 与 `XMLHttpRequest`。那会与
站点自己的封装、其他扩展、严格 CSP 冲突，出错时可能直接把站点搞坏 —— 代价明显大于收益，
所以本扩展不做。

**怎么判断你的图源属于哪一类**：在页面上对着裂掉的图右键「检查」。看到的是 `<img>` 且
`src` 就是图片地址，就属于能救的；如果 `src` 是 `blob:` 开头，或者根本找不到 `<img>`
（图画在 canvas 上、或是某个元素的背景），就属于救不回来的。

## 15. 「连不上代理就直连原图」会让重试整块失效

分流页的「全部失败后」有两个选项，它们对重试的影响是**决定性**的：

| 选项 | PAC 返回 | 代理连不上时 |
|---|---|---|
| 直连原图 | `PROXY a:1; DIRECT` | 浏览器静默改走直连，图片正常显示、**不派发 error** |
| 不直连 | `PROXY a:1` | 请求失败并派发 `error`，重试与兜底接手 |

选「直连原图」时，重试与兜底代理**一次都不会触发** —— 而且更糟的是，你的真实 IP 已经
交给图源了，界面上却什么异常都看不到。这正是本扩展最想避免的那类静默失败。

设置页对这个组合有一条常亮告警。新装默认仍是「直连原图」（宁可图能显示，也不要一上来
就整屏裂图），要用重试就必须自己改成「不直连」。

**另一个相关的空档**：当轮询池**空了**（节点全被禁用或全部不支持），PAC 无论选哪个都会
返回 `DIRECT` —— PAC 语法里没有「拒绝这个请求」的写法。所以「所有节点都挂了」这种情况
不会走到重试与兜底，而是直接直连。这一点由设置页顶栏和活动日志的红色告警负责喊出来
（「没有可用节点，当前全部直连」），不是靠重试兜。

## 16. 兜底图片代理会拿到你的图片地址

兜底走的是 URL 改写：重试全部失败后，`<img>` 的地址被换成
`https://兜底服务/?url=<原图地址>`。这意味着**兜底服务能看到你访问的每一张图的地址**，
用公共服务（wsrv.nl 之类）就等于把图源地址交给第三方。

兜底请求发往的是兜底服务自己的域名，**扩展会自动把这个域名加进绕过列表**，所以它一定
直连发出、不经轮询池 —— 好处是所有代理都挂了它照样能用（这正是兜底的意义），代价是这次
请求用的是你的真实 IP。

自动绕过是必要的：一条宽泛的规则（比如 `^https?://(img|cdn)\d*\.`）完全可能恰好命中
兜底服务的域名，那样取兜底图的请求会被送进同一个已经不好使的代理池，最后一道防线跟着一起挂。

如果这两点里有任何一条不能接受，就别启用兜底：把「兜底图片代理」留空即可，重试用尽后
图片直接裂开，不会有任何数据外发。

## 17. 内容脚本会注入到所有页面

重试必须由页面里的代码执行（原因见 [ARCHITECTURE.md](ARCHITECTURE.md) 决策 D20），
所以 `manifest.json` 声明了 `content_scripts: ["<all_urls>"]`。

这个脚本跑在**隔离世界**，并且刻意做得很笨：它不读页面内容、不发网络请求、不碰 cookie、
不修改页面全局对象，只做三件事 —— 监听资源加载失败、问后台该怎么办、按回复重新给
`<img>` 赋值。它也不持有任何规则（决策 D21），所以它连「这张图归不归本扩展管」都答不上来。

即便如此，这确实把扩展的权限面从「只改代理设置」扩到了「会向任意页面注入代码」。
这是实现「换个代理重发一次」的必要代价，没有别的路可走。
