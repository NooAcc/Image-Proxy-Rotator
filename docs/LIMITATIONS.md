# 技术限制

本文档说明本扩展**做不到什么**，以及为什么。这些都是浏览器扩展平台或网络栈的固有约束，
不是可以靠多写代码绕过的缺陷。

---

## 1. 只支持 HTTP / HTTPS 代理

**结论：可用的代理类型只有 `http://` 与 `https://`。**

浏览器扩展改变请求出口的唯一手段是 `chrome.proxy` API 的 PAC 脚本模式。PAC 脚本的
`FindProxyForURL()` 只能返回浏览器网络栈认识的少数几个关键字，而本项目只登记了
`PROXY`（HTTP 代理）与 `HTTPS`（HTTPS 代理）两种。

其他代理类型一律不受支持，粘贴时会被逐条提示并忽略：

| 类型 | 为什么不支持 |
|---|---|
| SOCKS4 / SOCKS5 | 已从支持范围中移除；且 Chromium 网络栈本身不支持 SOCKS 的用户名密码认证，带认证的节点无法可靠工作 |
| VLESS / VMess | 需要在原始 TCP 之上做自定义握手与加密。扩展拿不到原始 socket（`chrome.sockets.*` 只存在于已废弃的 Chrome Apps） |
| Hysteria2 / TUIC | 基于 QUIC，还带自定义拥塞控制。扩展既不能收发 UDP，也无法接入 QUIC 栈 |
| Trojan | 需要在 TLS 之上直接承载原始 TCP 流量 |
| Shadowsocks / SSR | 需要原始 TCP + 自定义流加密 |

**纯 JavaScript 无法实现上述任何一种协议的隧道**：扩展环境既没有原始 TCP/UDP socket，
也无法自行完成 TLS 握手并验证证书链。任何声称能在浏览器扩展内直接跑这些协议的方案，
实际上都依赖一个本地客户端在旁边转发。

**如果你手上只有这些类型的节点**，可行做法是在本机运行一个客户端（sing-box、Clash、
v2rayN 等），让它开一个**本地 HTTP 混合入口**，然后把那个本地地址（如
`http://127.0.0.1:7890`）当成普通 HTTP 代理加进本扩展。但要注意：这样只有一个出口，
达不到「多 IP 分流」的目的 —— 除非本地客户端开多个端口、每个端口对应不同的上游出口，
再把这些端口逐个加进来。这属于用户自行搭建的环境，本扩展不再提供相关配置生成能力。

---

## 2. HTTPS 目标需要代理支持 CONNECT

漫画图片绝大多数是 `https://`。浏览器经 HTTP 代理访问 HTTPS 资源时，必须先向代理发
`CONNECT` 建立隧道。如果代理只允许明文 HTTP 转发、或禁止 `CONNECT` 到 443 以外的端口，
节点会表现为「看起来在线，但图片全失败」。

**本扩展的应对**：默认测速地址是 `https://` 开头，因此一次测速就等价于验证了这条
CONNECT 通路。测速能过、图片却失败，通常是目标站点或规则的问题，不是代理不支持 CONNECT。

---

## 3. 代理凭据不能写进 PAC

PAC 语法里没有携带账号密码的位置（`PROXY user:pass@host:port` **不是**合法写法）。

**本扩展的应对**：用 `chrome.webRequest.onAuthRequired`（需要 `webRequestAuthProvider`
权限）在浏览器要求认证时按 `主机:端口` 匹配到对应节点并自动应答，用户不会看到认证弹框。
凭据只存在 `chrome.storage.local`，不会出现在 PAC 脚本里 —— 这一点有单元测试守着。

同一请求第二次要求认证时扩展会停止应答（说明凭据不对），交还给浏览器弹框，避免无限重试。

---

## 4. HTTP/2 连接复用会降低分流粒度

即使 PAC 为每个请求返回不同节点，浏览器仍可能把多个请求塞进**已经建立**的连接里 ——
HTTP/2 的多路复用就是为此设计的。结果是「几十张图片只用到了少数几个节点」。

这是网络栈行为，PAC 层面无法否决。

**缓解办法**
- 节点数 ≥ 4，池子越大越容易被摊开
- 「每几个请求换一次节点」保持默认值 1
- 图源分布在多个域名时效果更好（不同域名不共享连接）

**如何确认分流真的生效**：看状态页「最近活动」里的**出口 IP**。同一批图片出现多个不同 IP
就是硬证据；全是同一个 IP 说明连接被复用了。

---

## 5. Chromium 自带「坏代理」列表

连接失败的代理会被浏览器自己拉黑约 5 分钟，期间即使 PAC 返回它也会被跳过。

这会与本扩展的自动禁用叠加，表现为「刚失败的节点在扩展里还显示可用，但实际没被使用」。
属于双重保护，不是缺陷。等待几分钟或手动点「重置」即可。

---

## 6. 浏览器代理设置是独占资源

`chrome.proxy` 一次只能由一个扩展控制。若另一个代理类扩展先占了，或企业策略强制了代理，
本扩展的设置会被忽略。

**本扩展的应对**：每次注入后读取 `levelOfControl`，不是 `controlled_by_this_extension`
时在设置页和状态页顶部显示红色告警，而不是假装成功。

---

## 7. 测速地址必须允许跨域

测速请求由扩展的 Service Worker 用 `fetch` 发出，会受 CORS 约束。默认地址
`https://cp.cloudflare.com/generate_204` 返回 204 且允许跨域，适合做探针。

换成不返回跨域响应头的地址，测速会统一失败并提示「探测地址不支持跨域」。此时换回默认地址即可。

---

## 8. PAC 失败时的行为

注入 PAC 时使用 `mandatory: false`。含义是：PAC 脚本执行出错时浏览器**直连**，而不是断网。

同时生成的 PAC 顶层包着 `try/catch`，任何内部异常都返回 `DIRECT`。这是刻意选择的安全默认值 ——
一条手误的正则最坏结果是「不走代理」，绝不会是「整个浏览器上不了网」。

用户输入的正则在写入配置前就会被 `new RegExp()` 预校验，非法的直接拒绝保存；
历史配置里的非法正则在加载时被丢弃，并在设置页标红说明。

---

## 9. Service Worker 会休眠

MV3 的后台是 Service Worker，空闲时会被回收。因此：
- 定时测速用 `chrome.alarms`（能唤醒 SW），不用 `setInterval`
- 轮询计数器活在 PAC 脚本自己的作用域里，不依赖 SW 常驻
- 日志与统计写进 `chrome.storage.session`，SW 被唤醒后能接上

`chrome.alarms` 的最小周期是 1 分钟，所以定时测速间隔填小于 1 的值会被提升到 1。

---

## 10. 历史配置中的不支持节点

早期版本曾计划支持 SOCKS 与若干高级协议。如果你的配置里还留着这类节点：

- 它们**不会**参与分流（`pacToken()` 对它们返回 `null`，因此进不了 PAC 节点池）
- 加载时后台日志会给出明确告警
- 设置页会把它们标红为「不支持」，启用开关被禁用
- 可点「清除不支持的节点」一键删除

不会出现「静默参与分流」的情况 —— 这一点由单元测试覆盖。
