# 人工验收清单

自动化测试（`npm run verify`）覆盖不到的部分只剩一类：**必须有真实网络或真实浏览器渲染
才能判定**的行为。这份清单就是那一类，需要人在浏览器里走一遍。

已经自动化、**不需要**再人工确认的（这些出问题 `npm test` 会先红）：PAC 注入参数与路由决策、
**生成的 PAC 是纯 ASCII**、中文域名转 Punycode、**HTTPS 下 path/query 被剥掉后的退化匹配**、
**测速定向 PAC 的注入与恢复**、连续失败自动禁用后 PAC 不再选中该节点、自动恢复、定时任务重建、
混合粘贴的分类与提示文案、不支持的节点被挡在分流之外、消息契约的成功与异常路径、
认证应答与二次挑战、观测层不改节点状态、**统计的累加/剪枝/汇总与落盘**、
**「命中规则」与「按规则送去代理」的分离计数**、**共用地址节点的归因（不硬猜）**、
**缓存命中被排除在总量与耗时之外**、**延迟分位数落在正确的桶里**、
**「页面没捕获」与「结果未知」两个口径**、**测速的互斥保护**、SW 冷启动流程与事件注册，
以及两套主题的配色对比度、页面 id 契约、分段控件三处一致、节点状态的三重编码、
指标卡与占比条的产物结构、**每个统计口径在面板上都有落点**。

> **第 5 步是这份清单里最重要的一条。** 1.2.0 通过了当时全部 271 个自动化测试，却一个
> 请求都没代理出去 —— 因为测试和扩展犯了同一个错误假设。只有真实代理后台的流量数字
> 能揭穿这类故障。

## 1. 加载扩展

Edge 打开 `edge://extensions` → 开启「开发人员模式」→「加载解压缩」→ 选仓库根目录
（Chrome 同理，地址是 `chrome://extensions`）。

**预期**：无红色报错，Service Worker 控制台干净。

## 2. 两个页面的实际渲染

设置页五个分区（统计 / 节点 / 规则 / 分流 / 诊断，默认落在「统计」）、侧栏切换与浏览器
前进后退、弹窗 380×600 固定布局与四个视图切换、深色与亮色两套主题、860px 以下窄屏
（侧栏变顶部横向导航，键值清单退回上下堆叠）。

粘贴下面这段，确认提示逐条正确：

```
http://1.2.3.4:8080#好节点
https://5.6.7.8:8443#另一个好节点
socks5://user:pass@9.9.9.9:1080#SOCKS节点
vless://11111111-2222-3333-4444-555555555555@v.example.com:443?security=tls#VLESS节点
这是垃圾行
```

**预期**：入库 2 个；3 条显示 `本程序不支持该代理类型，仅支持 HTTP/HTTPS 代理` 且开关变灰；
1 条「无法识别」。

## 3. 真实测速

填入至少 2 个**真实可用**的 HTTP/HTTPS 代理 → 点「一键测速」。

**预期**：显示真实毫秒数与对端 IP；测速是**逐个串行**的，节点多时会看到延迟数字一个一个
出现；不可用节点连续失败 2 次后变灰并标「已自动禁用」。

**必须一起看的**：代理服务商后台应当出现**与节点数相同**的连接记录。一条都没有就说明
定向没生效，测出来的数字是直连的延迟 —— 这正是 1.2.0 的故障。

顺手验一条负例：临时把「测速地址」改成一个不存在的域名（如 `https://nope.invalid/x`），
测速应当**失败**而不是给出一个漂亮的延迟。

## 4. 规则 + 总开关

加一条「域名」类型的规则，填你图源的域名 → 打开总开关。

**预期**：弹窗状态变「已生效（N 节点 / M 规则）」。

## 5. ★★ 分流硬证据（最重要的一条）

打开一话漫画（几十张图），然后**同时**看三处：

| 看哪里 | 预期 |
|---|---|
| 设置页「统计」→ 请求统计 | 「按规则送去代理」是非零数；「规则命中但直连」是 **0** |
| 弹窗「活动」里的**对端 IP** | 同一批图片出现**多个不同 IP** |
| **代理服务商后台** | 有连接、有流量，且量级与图片数相称 |

三处必须互相印证。**尤其是第三处** —— 前两处都可能被扩展自己的错误假设骗过，
代理商后台的流量数字骗不了人。

若「规则命中但直连」不为零：规则依赖了 HTTPS 下看不见的路径，改成「域名」类型。
活动日志里会有一条说明，写明浏览器实际交给分流脚本的是什么。

若对端 IP 全是同一个：多半是 HTTP/2 连接复用（见 [LIMITATIONS.md](LIMITATIONS.md) 第 4 节），
可增加节点数或换多域名图源再看。

**这是唯一无法在 Node 里模拟的判据。**

**预期**：**不弹认证框**，图片正常加载，日志出现「已为节点「X」自动提供代理凭据」。

## 9. 统计面板

走完第 5 步（真实分流过一批图片）之后看设置页的「统计」分区。

**预期**：
- 「命中规则」与「按规则送去代理」都是非零数，且**两者相等**（差值就是「规则命中但直连」）
- 「对端确认是代理」也是非零数 —— 这是「真的从代理回来了」的硬证据
- 成功率、耗时中位数、慢的那一成（p90）都有值，且 **p90 ≥ 中位数**
- 「节点使用分布」：**节点地址各不相同**时至少一个节点有次数、占比加起来 100%；
  节点是同一台机器的多个端口时整张表会收起来，见下面那条
- 「规则命中」里启用的那条规则有命中数；没启用的规则显示 0 次
- 面板每 5 秒自动刷新；切到别的分区再切回来数字继续涨
- **重启浏览器后数字仍在**（这是 `storage.local` 与 `storage.session` 的区别，
  也是这一条必须人工验的原因）
- 点「清零统计」→ 全部归零，但节点、规则与设置都没变；「活动」里的日志也还在

顺手验一下删除节点后的占比诚实性：删掉一个已经有用量的节点 → 表格里出现
「已删除的节点（历史累计）」一行，占比总和仍是 100%。

**验一条缓存口径（1.4.1 修的核心之一）**：记下此刻的「走代理的请求」与「缓存命中」，
然后按 <kbd>←</kbd> 退回上一页、再 <kbd>→</kbd> 前进回来（**不要**按刷新，那会绕过缓存）。

- 「缓存命中」应当增长
- 「走代理的请求」**几乎不增长** —— 图片是从缓存读的，一个字节都没出去
- 「耗时中位数」不该被拉低到个位数毫秒

反过来，硬刷新（<kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd>）时「走代理的请求」应当
成批增长，「缓存命中」基本不动。**两个数字一起涨就是回归了** ——
说明 `details.fromCache` 又没被读（见 [LIMITATIONS.md](LIMITATIONS.md) 第 14 节）。

**如果你的节点是同一台机器的多个端口**：整张表应当**收起来**，只留一条橙色说明，
写明「你的 N 个节点全在 X 上，只有端口不同」，请求全部计入「无法归因」。这是正确行为 ——
浏览器不给对端端口，分不出来，逐行列出 19 个 0 只会让人以为轮询坏了。
**表格里出现「1 个节点 100%、其余全 0%」就是回归了**（见 [LIMITATIONS.md](LIMITATIONS.md) 第 13 节）。

顺手对一下口径：此时「无法归因」应当 ≈「对端确认是代理」，而**不该**等于「走代理的请求」——
连接层就失败的那些请求没有对端 IP，不该算成归因失败。

## 10. 测速的互斥

一轮测速进行中（节点多时会持续几十秒）再点一次「一键测速」，或同时点某个节点的单独测速。

**预期**：第二次操作被明确拒绝，日志出现「正在测速中，请等待当前一轮完成后再试」；
**不会**出现两轮交错、也不会有节点拿到别人的延迟数字。第一轮照常跑完。

## 11. ★ HTTPS 下路径不可见（1.2.1 修复的核心，务必验）

加一条**正则**类型的规则，内容填 `\.(jpe?g|png|webp)$`，启用它，然后关掉其他规则，
打开一话漫画。

**预期**：
- 统计里「命中规则」在涨，而「按规则送去代理」保持 **0**，「规则命中但直连」等于「命中规则」
- 活动日志出现**一条**（不是几百条）说明，写明浏览器实际交出去的是
  `https://<图源域名>/`，并建议改用「域名」类型
- 规则列表里这条规则下方有提示，说明它对 HTTPS 不生效
- 规则测试器输入一个真实图片 URL 后，同时给出两个结论：完整 URL 命中、分流脚本判定不了

然后把它改成「域名」类型 → 「按规则送去代理」开始增长，「规则命中但直连」不再增加。

再验一条「退化」：加一条**前缀**类型的规则，内容 `https://<图源域名>/img/`。
规则列表下方应说明「HTTPS 下实际按 `https://<图源域名>/` 整段生效，范围比你写的更宽」。

## 12. 中文域名与非 ASCII 规则

在「规则」分区加一条**域名**类型的规则，内容填 `漫画.com`；再加一条**正则**类型的，
内容也填 `漫画`。

**预期**：
- 保存后活动日志出现「代理规则已生效」，**不出现** `pacScript.data` 相关的报错
  （这是修复前的症状：整份 PAC 注入失败，扩展表面上什么都没做）
- 「诊断」→「当前生效的 PAC 脚本」里，中文全部是 `\uXXXX` 形式，域名规则里能看到
  `xn--qex62k.com`；整份脚本找不到一个中文字符
- 正则那条规则下方出现提示，说明它含非 ASCII 字符、可能永远命中不了，建议改用域名类型

## 13. ★★ 重试真的换了代理

自动化测试验的是「判定对不对」，验不了「重发之后真的落到了另一个出口」—— 那需要多个真实代理。

**准备**：至少 2 个能用的节点；「分流」分区把「全部失败后」设为 **不直连**，
「每张图最多尝试」保持 3，「每几个请求换节点」保持 1。

**制造一次真实失败**：把其中一个节点的地址改成一个连不上的端口（例如把 `:8080` 改成 `:8081`），
或者直接在代理服务器上把它停掉。**不要**用「禁用」开关 —— 那样它根本进不了轮询池，
不会产生连接失败。

**预期**：
- 打开一话漫画，图片仍然全部显示出来（坏节点的那几张被重发救回了）
- 「统计」→「重试与兜底」里，「重试」和「重试救回」都是非零数，两者接近
- 弹窗「最近活动」里出现一条「……的图片加载失败（代理故障），正在换一个节点重发」，
  **且同一个域名每分钟最多一条** —— 刷屏说明日志节流坏了
- 「最近活动」里同一批图片出现**多个不同的对端 IP**

**反向验证（必须做）**：把「全部失败后」改回 **直连原图**，刷新页面。
「重试」应当**一次都不涨** —— 因为代理连不上时浏览器静默走了直连，图片正常显示、
不派发错误事件。设置页此时应有一条常亮告警说明这件事。这条反向验证证明那条告警不是摆设。

**再验一条「不该重试的不重试」**：找一个确定 404 的图片地址（在图源域名下随便编一个路径），
直接在地址栏打开它。「重试」不该增长，「判定为不重试」应当 +1 —— 换个代理拿到的还是同一个 404。

**再验一条「页面没捕获」**：找一个用 `new Image()` 预加载大图的阅读器（多数漫画阅读器
都是），在代理全挂的状态下翻几页。

- 「页面没捕获」应当增长，而「重试」几乎不动
- 卡片下方出现橙色告警，说明重试机制碰不到这些图

这不是缺陷，是浏览器扩展的能力边界（见 [LIMITATIONS.md](LIMITATIONS.md) 第 16 节）。
**它必须能被看见** —— 上一版这一格不存在，于是「未重试」显示 0，
读起来像「每次失败都重试了」。

**再验一条「结果未知」**：在图片正在重发的时候（把 `delayMs` 调大到 3000 更容易抓）
立刻关掉标签页或者点浏览器后退。

- 「结果未知」应当 +1，而「重试救回」不动
- 「重试」减去「救回 + 用尽 + 结果未知」= 「还没有结论」，四个数字对得上

**四格对账**：任何时刻都该有
`重试 = 重试救回 + 用尽仍失败 + 结果未知 + 还没有结论`。**对不上就是回归了** ——
上一版正是因为没有「结果未知」，实测「重试 7 / 救回 6」里那 1 次差额无处可查。

## 14. 兜底代理

**准备**：「兜底代理」填一个真的能用的 HTTP 正向代理（`10.0.0.3:37581` 这种形态即可），
勾上「启用兜底代理」；把**全部**节点都改成连不上的端口，让重试必然用尽。
「全部失败后」保持「不直连」—— 选「直连原图」的话兜底一次都不会触发（第 4 节）。

**预期**：
- 打开漫画页，图片仍然能显示（经兜底代理取回）
- 「统计」里「用尽仍失败」与「兜底接管」同步增长，「兜底成功率」出现数字
- 「最近活动」里出现「…… 的图片在 N 个节点上都失败了，已切到兜底代理。」，
  且说明里点明**这个图源接下来 12 秒的所有请求都会走兜底代理**
- 开发者工具里那张图的请求确实指向兜底代理（或者在代理自己的访问日志里能看到）

**验窗口是按「源」生效的**：兜底刚触发之后立刻在同一个图源上再取一张**本来正常**的图。
它也会走兜底代理 —— 这不是缺陷，是 MV3 表达能力的边界
（见 [LIMITATIONS.md](LIMITATIONS.md) 第 18 节）。反过来，**另一个**图源同一时刻应当
照旧走轮询池，互不牵连。

**验冷却**：让同一个图源连续失败超过 12 秒。
- 第 12 秒之后窗口关闭，该源回到轮询池（依旧全挂，于是继续裂图）
- 接下来 30 秒里用尽的图**不再切兜底**，「冷却期跳过」那一格开始增长
- 过了 30 秒再失败，「兜底接管」才会继续涨

**验它不会被自动禁用**：兜底代理不在节点列表里，所以健康探测与自动禁用对它无效
（这是设计要求：最后一道防线不该自我禁用）。把兜底代理也改成连不上的端口再试：
- 图片裂开，「兜底接管」照常增长而「兜底成功率」掉下去
- 节点列表里**不该**多出一行，顶栏也不该报「兜底节点被禁用」
- 这正是它唯一的失效表现 —— 只能从这两个数字看出来

**验填错地址不会静默生效**：把兜底代理填成 `http://10.0.0.3:37581/?url={url}`
（1.4.x 的改写型模板写法）。
- 输入框下方**当场**给出中文原因，指出带路径/查询串的是改写型图片服务
- 保存后开关被自动关掉，且卡片里说明它为什么自己关了
- **不能**出现「填了、开着、真用到时每次 400」这种状态 —— 那正是 1.4.x 栽的跟头

## 15. 内容脚本不打扰无关页面

打开几个与图源无关、且本来就有裂图的网站（随便找即可）。

**预期**：
- 这些页面的裂图**不会**被重发（网络面板里同一个地址只出现一次）
- 「统计」里的「重试」不增长
- 关掉总开关后再逛，扩展应当在第一张裂图之后进入冷却，不再逐张询问后台

## 16. 开发者调试日志

自动化测试验的是「记不记得下、导不导得出」，验不了「浏览器里点下去真的会下载几个文件」——
那要真实的下载栈。

设置页 →「诊断」→「开发者调试日志」，打开开关。

**预期**：状态行变成「已开启：0 条 …」；此时打开一话漫画，回来刷新这一屏，
条数应当在涨，并列出 `pac`、`request`、`retry`、`content`、`msg`、`ui` 这些环节各多少条。

然后点「导出（每环节一个文件）」。

**预期**：
- 浏览器就「是否允许下载多个文件」问一次，同意后拿到多个 `.log`
- 随便打开一个：前五行是 `#` 开头的文件头，含扩展版本号、命名空间、条数与那句隐私警告
- `request` 那份里能看到完整 URL、状态码、对端 IP，以及 `routed=` 与 `blind=` 两个**分开**的结论
- `content` 那份里能看到 `caught` / `resent` / `loaded` —— 这是后台看不到的那半截
- **`ui` 那份里不该出现 `debugPush` / `getDebug`** —— 出现了就是自噬防护漏了，
  日志会开始记录日志自己，条数在你什么都不做的时候持续上涨

再点「合并导出为一个文件」，确认拿到一份行首多一列环节名的 `ipr-debug-all-*.log`。

**关掉开关**。

**预期**：状态行回到「未开启」；再点导出会明确提示「还没有记录到任何调试日志」，
而不是给出一份上一次复现留下的旧文件。

顺手验一条：开着开关重启浏览器，条数应当归零（日志存在会话存储里，这是有意的）。
而**只是关掉设置页再打开**、或者等 Service Worker 休眠之后再看，条数应当还在。

## 17. ★ 轮询到底均不均匀

**这一条扩展自己回答不了**，必须外部验证 —— 浏览器只给对端 IP、不给对端端口
（见 [LIMITATIONS.md](LIMITATIONS.md) 第 13 节）。两条路，任选其一：

**办法 A：看代理服务商后台的分端口流量。** 最省事，也最接近真相。跑完一话漫画后
看各端口的请求数/流量是否接近。这是同址多端口配置下**唯一**的日常验证手段。

**办法 B：临时换一批地址唯一的节点跑一轮。** 只在怀疑轮询本身坏了时做：

1. 导出当前配置备份（设置页 →「导入导出」）
2. 换成 3–4 个**host 各不相同**的节点（不同机器，或不同的公网出口）
3. 打开一话漫画，回到「统计」→「节点使用分布」

**预期**：每个节点都有次数，占比接近均等（±20% 以内，图片数越多越均匀），
「无法归因」接近 0。

**这一步不通过才是真的轮询坏了。** 注意两个正常的干扰因素：
HTTP/2 连接复用会让分布偏斜（见 [LIMITATIONS.md](LIMITATIONS.md) 第 4 节）；
「每几个请求换一次节点」不是 1 时分布本来就是块状的。

验完记得导回备份。
