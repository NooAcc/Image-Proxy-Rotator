# 漫画图片代理分流（Image-Proxy-Rotator）

[![构建与发布](https://github.com/NooAcc/Image-Proxy-Rotator/actions/workflows/build.yml/badge.svg)](https://github.com/NooAcc/Image-Proxy-Rotator/actions/workflows/build.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

一个 Manifest V3 的 Edge / Chrome 扩展：把匹配规则的图片请求按**轮询**分散到多个
**HTTP / HTTPS 代理**上，绕过漫画站的单 IP 速率限制。

漫画站在阅读时会一次性预加载整章图片，几十个并发请求打在同一个出口 IP 上，很容易触发
站点限流，表现就是「部分图片一直转圈或裂图」。本扩展让这些请求轮流从不同代理出去，
把并发压力摊开。

> **支持范围：仅 HTTP / HTTPS 正向代理。**
> SOCKS4 / SOCKS5 / VLESS / VMess / Hysteria2 / Trojan / Shadowsocks 等类型**不受支持**，
> 粘贴后会被逐条提示并忽略，也绝不会参与分流。原因见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md)。

## 安装

本扩展零依赖、零构建，源码即产物。两种装法任选：

**A. 下载现成的包**（推荐给只想用的人）

到 [Releases](https://github.com/NooAcc/Image-Proxy-Rotator/releases) 下载
`image-proxy-rotator-*.zip` 并解压。标着 `Pre-release` 的是每次提交自动构建的开发版，
不带该标记的是正式版。

**B. 直接克隆源码**

```bash
git clone https://github.com/NooAcc/Image-Proxy-Rotator.git
```

然后加载（两种方式都一样）：

**Edge**
1. 打开 `edge://extensions`
2. 打开左下角「开发人员模式」
3. 点「加载解压缩的扩展」，选择解压出来的目录 / 仓库根目录（含 `manifest.json` 的那一层）

**Chrome**：同理，地址是 `chrome://extensions`，按钮叫「加载已解压的扩展程序」。

装好后工具栏会出现一个分流图标，点它打开状态面板。

> `.crx` 不提供 —— 开发人员模式解锁的是「加载解压缩」，并不等于允许安装本地 crx，
> 自签名 crx 会被现代 Chromium 以缺少商店签名为由拒绝。详见 [docs/PACKAGING.md](docs/PACKAGING.md)。

## 5 分钟上手

1. **打开设置** —— 点扩展图标 →「打开设置」。

2. **添加节点** —— 在「批量导入」里每行粘贴一个代理，然后点「添加节点」：

   ```
   http://1.2.3.4:8080#节点A
   https://proxy.example.com:8443#节点B
   http://用户名:密码@5.6.7.8:3128#节点C
   10.0.0.5:3128
   ```

   节点数量建议 **≥ 4**，分流效果才明显。

3. **配置规则** —— 加一条 `域名` 类型的规则，填漫画站的图片域名（例如 `cdn.manga.com`）。
   也可以点「插入常用预设」，会加入 3 条候选规则（**默认关闭**），确认后逐条启用。

   > **务必优先用「域名」类型。** HTTPS 请求交给分流脚本时，浏览器只给出
   > 「协议 + 域名 + 端口」，路径和查询串会被剥掉。所以像 `\.jpg$` 这种按扩展名匹配的
   > 规则对 HTTPS 图片**永远命中不了** —— 而且不报错，只是安静地直连。详见
   > [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 12 节。

4. **测速** —— 点「一键测速」。每个节点会依次真的从该代理出去一趟，显示真实延迟；
   连接不上的节点在连续失败达到阈值后会被自动禁用并从轮询中剔除。
   测速期间会临时接管浏览器代理设置（一次只能定向一个节点），测完自动恢复。

5. **打开总开关** —— 页面顶部的开关。

6. **验证生效** —— 打开一话漫画，然后切到设置页的「统计」分区：
   **「按规则送去代理」必须是个非零数**，而「规则命中但直连」应当是 0。
   再点扩展图标看「最近活动」，如果同一批图片的日志里出现了多个不同的对端 IP，
   说明分流真的生效了。

7. **重试默认就是开的** —— 代理连不上时扩展会换下一个节点把这张图重新请求一次，
   默认最多尝试 3 个节点。因为「全部失败后」默认是**不直连**，代理不通会真的裂图
   而不是悄悄降级成直连 —— 所以**如果整屏都是裂图，先回到第 4 步测速**，那说明节点
   本身不通。还想更保险的话，填一个「兜底代理」；阅读器用 `fetch` / 预加载取图的
   站点还可以开「深度重试」。细节与代价见下面的
   [重试是怎么工作的](#重试是怎么工作的)。

## 图片没走代理？先看这两个数字

统计面板里有两项刻意分开的计数：

| 指标 | 含义 |
|---|---|
| **命中规则** | 按你写的规则，本该走代理的请求数 |
| **按规则送去代理** | 其中浏览器真正交给分流脚本判定并路由出去的数 |
| **规则命中但直连** | 两者的差值。**不为零就是规则写错了** |
| **对端确认是代理** | 响应来自你某个节点的地址 —— 「真的从代理回来了」的硬证据 |

「规则命中但直连」不为零，几乎总是同一个原因：规则依赖了 HTTPS 下看不见的路径。
把它改成「域名」类型即可。活动日志里也会给出一条说明，写明浏览器实际交出去的是什么。

## 「节点使用分布」里只有一个节点在动？

如果你的节点是**同一台机器的不同端口**（`10.0.0.3:24000`、`10.0.0.3:24001`…），
这张表**无法**告诉你哪个节点在干活，请求会全部计入「无法归因」。

原因：浏览器只告诉扩展对端的 **IP**，不给端口。同一台机器的几十个端口在扩展眼里
是同一个地址。1.2.1 及更早版本会把全部用量记到列表里第一个节点上，于是显示
「1 个节点 100%、其余全 0%」—— 那是归因在编数字，不是轮询坏了。

现在扩展分不出来就说分不出来，并在表格上方标明共用了哪个地址、有几个节点；
**全部节点都共用地址时这张表会整个收起来** —— 逐行列出一片 0 只会让人以为轮询坏了。
**想确认轮询是否均匀，请看代理服务商后台的分端口流量。** 详见
[docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 13 节。

## 统计面板

设置页打开就是「统计」分区，回答四个问题：

| 卡片 | 回答什么 |
|---|---|
| 运行状态 | 现在到底生效没有、控制权在谁手上、上次注入分流脚本是什么时候、注入与测速失败了多少次 |
| 请求统计 | 命中规则的总数、其中按规则送去代理多少、对端确认走通多少、成功率、耗时中位数与 p90、缓存命中、有多少次归不到具体节点 |
| 重试与兜底 | 重试了几次、救回几张、用尽仍失败几张、有几次结果未知、有几次页面压根没捕获到、兜底接管几次 |
| 节点使用分布 | 哪个节点在干活、各自占比多少、成功率如何（节点共用地址时无法区分，见上一节） |
| 规则命中 | 哪条规则在起作用；**命中 0 次的规则会露出来** —— 那通常意味着规则写错了 |

弹窗里的「统计」标签是同一份数据的精简版（各取前 5 名）。

几点说明：

- 计数**跨浏览器重启累计**，存在本机 `chrome.storage.local`。想归零点「清零统计」——
  它只动统计数字，不碰节点、规则和设置。
- 只统计**命中了你的规则**的请求；其余请求本就该直连，不计入。成功的判定是 HTTP 状态码小于 400。
- **开启重试之后成功率会变低，这是正常的**：重发是一次全新的请求，会被如实计进总量。
  用「重试」那一格对账。「重试救回」是重发之后真的加载成功了，不是估算出来的。
- 「无法归因」是诚实的一项：归因靠请求的对端 IP（走代理时对端就是代理本身），而浏览器
  **只给 IP、不给端口**。所以同一台机器的多个端口无法区分，节点写成域名时也要先测速一次
  才认得出。这些请求单独计数，不会硬塞给某个节点凑一个好看的数字。
- 只存聚合计数，不留请求明细，所以占用不随使用时长增长（满配 500 节点 + 500 规则实测 31.5 KB）。
   代价是没有历史趋势图 —— 需要的话见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) 决策 D14。

## 节点格式

| 写法 | 说明 |
|---|---|
| `http://主机:端口` | HTTP 代理，缺端口默认 80 |
| `https://主机:端口` | HTTPS 代理（到代理本身的连接加密），缺端口默认 443 |
| `http://用户名:密码@主机:端口` | 带 Basic/Digest 认证，扩展会自动应答，不会弹框 |
| `主机:端口` | 按 HTTP 处理 |
| `主机:端口:用户名:密码` | 常见订阅格式，按 HTTP 处理 |
| `http://[2001:db8::1]:8080` | IPv6 需带方括号 |
| 行尾 `#名称` | 给节点命名，可选 |
| 行首 `#` / `//` / `;` | 注释行，会被跳过 |

也可以把整段 base64 订阅内容直接粘进去，扩展会先解码再逐行解析。
其中非 HTTP/HTTPS 的条目会被逐条列出并忽略。

## 规则类型

只有命中规则的请求才走代理，其余保持直连。规则**按列表顺序**匹配，命中第一条即生效。

| 类型 | 示例 | 命中 | HTTPS 下 |
|---|---|---|---|
| 域名 | `manga.com` | `manga.com` 及其所有子域（不会误命中 `notmanga.com`） | **完全按预期** |
| 正则 | `^https?://(img\|cdn)\d*\.` | 匹配整条 URL 的正则 | 只能约束域名部分 |
| 前缀 | `https://cdn.manga.com/img/` | 该路径下的全部请求 | 退化成整个 `https://cdn.manga.com/` |
| 通配 | `https://*.manga.com/img/*.jpg` | `*` 匹配任意字符 | 退化成整个 `https://*.manga.com/` |
| 精确 | `https://cdn.manga.com/1.jpg` | 完全相同的 URL | 退化成整个 `https://cdn.manga.com/` |

**最后一列很重要。** 浏览器交给分流脚本的 https 网址里，**路径与查询串已被剥掉** ——
`https://cdn.manga.com/img/001.jpg` 到那里只剩 `https://cdn.manga.com/`。所以：

- **「域名」类型是唯一天然安全的**，请优先用它
- 依赖扩展名或路径的正则（`\.jpg$`、`/images/`）对 HTTPS 图片**永远命中不了**
- 前缀 / 通配 / 精确会自动退化到「同源」这一层：能生效，但范围比你写的更宽

这三种情况都会在规则列表下方给出提示，统计面板也会把「规则命中但直连」单独计数。
详见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 12 节。

**中文域名**请用「域名」类型：浏览器交给分流脚本的网址里，域名已经是 Punycode 形式
（`漫画.com` → `xn--qex62k.com`），只有「域名」类型会自动完成这个转换。其余四种类型是整条
URL 的模式，无法可靠判断哪一段是域名，所以填了中文会在规则列表下方给出提示，说明它可能
永远命中不了。详见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 11 节。

**规则测试器**：设置页底部可以输入一个图片 URL，立刻看到浏览器实际会把什么交给分流脚本、
它会不会走代理、命中哪条规则、会在哪些节点间轮询。配规则时用它验证比刷页面快得多。

每条规则还可以**绑定节点子集**（不选则使用全部可用节点），适合「A 图源用这几个节点、
B 图源用另外几个」的场景。绑定的节点全部不可用时会自动回落到全部可用节点。

## 分流与测速设置

| 设置 | 含义 |
|---|---|
| 分流策略 | `轮询`=每个请求换一个节点；`哈希`=同一 URL 固定走同一节点（便于缓存与排查） |
| 每几个请求换一次节点 | 默认 1。调大可减少连接建立次数，但分流粒度变粗，也会削弱重试的效果 |
| **每张图最多尝试几个节点** | 默认 3（含首次）。代理连不上时换下一个节点重新请求一次，`1` = 不重试 |
| **重发前等待** | 默认 300 毫秒。留时间让浏览器把刚失败的代理登记进它自己的坏代理列表 |
| **全部失败后** | **默认 `不直连`**：代理不通就让请求真的失败，交给重试与兜底处理。改成 `直连原图` 则图一定能显示，但会暴露真实 IP，**且重试、深度重试、兜底三样都不会生效** |
| **兜底代理** | 重试全部失败后，把该图源临时切到这个代理再重发一次。填「地址:端口」，独立于节点列表 |
| **深度重试站点** | 一行一条。填了的站点会被额外注入补丁，让 `fetch` / `XHR` / `new Image()` 的失败也能重试。**只重发 GET / HEAD** |
| 测速地址 | 默认 `https://cp.cloudflare.com/generate_204`（返回 204 的极小响应，允许跨域） |
| 超时 | 超过该时间未响应即判为失败 |
| 定时测速间隔 | 分钟，`0` 关闭。最小生效值为 1 分钟（浏览器限制） |
| 连续失败几次后自动禁用 | 默认 2（只由测速结果驱动，线上请求失败不会禁用节点） |
| 绕过列表 | 这些主机永不走代理；本地地址与私有网段始终绕过 |

### 重试是怎么工作的

代理连不上时，扩展让页面把这张图**重新请求一次**。新请求会落到轮询里的下一个节点，
而刚失败的那个已经被浏览器自己排除了。**一个请求始终只挂一个代理**，所以重试不会让
某个节点替另一个节点顶班，轮询依然均匀。

三件必须知道的事：

1. **「全部失败后」必须是「不直连」**，重试才会生效 —— 这是 1.4.4 起的默认值，一般不用动。
   改成「直连原图」的话，代理连不上会被浏览器静默改走直连：图片正常显示、不报错，扩展
   什么都收不到，而真实 IP 已经交给图源了。设置页对那个组合有常亮告警。
   反过来说，**保持默认时节点不通就会真的裂图** —— 那是准确的反馈，先去测速。
2. **默认只有 `<img>` 救得回来。** 页面用 `new Image()` 预加载、或用脚本取 blob 再塞进
   `<img>` 的阅读器不派发可捕获的错误事件。判断方法：对着裂图右键「检查」，看到
   `<img src="http...">` 就是默认能救的；不是的话开「深度重试」（见下）。CSS 背景图与
   canvas 两种情况都救不回来。
3. **图源返回 404 / 5xx 时不重试** —— 换个代理拿到的还是同一个结果。

### 深度重试站点

默认的重试只盯着 DOM 里的 `<img>`。而漫画阅读器普遍用 `new Image()` 预加载下一页、
或者用 `fetch` / `XHR` 取图和调接口 —— **那些请求裂了，扩展收不到任何通知**，调高重试
次数一点用都没有。统计页的「页面没捕获」那一格就是在数这类失败。

在设置页把站点填进「深度重试站点」，扩展会给这些站点额外注入一小段代码，包住页面自己的
`fetch`、`XMLHttpRequest` 与 `Image`，让它们的网络失败也能换个节点重发一次。填法：

```
nhentai.net                      ← 直接写域名，自动覆盖子域名
https://noymanga.com/read/*      ← 或写完整匹配范围，收窄到具体路径
```

四件必须知道的事：

1. **它只装在你填的站点上。** 这段代码跑在页面自己的 JS 环境里（主世界），理论上可能与
   站点自己的封装冲突。没填的站点一个字节都不会被注入 —— 填之前请确认你信任这个站点，
   出问题就把那一行删掉。
2. **只重发 GET / HEAD。** 发评论、点收藏这类请求一律原样报错，绝不重复提交。
3. **`fetch` 之外的两条路，页面会先看到一次失败**（浏览器同步派发 error，补丁插不进去）。
   如果站点在错误处理里做了「永久标记失败」，可能出现双重处理。
4. **CSS 背景图、canvas、地址栏直接打开的地址仍然救不回来** —— 前两者不产生任何脚本可见
   的失败信号，后者页面里根本没有脚本。

装上没装上，看统计页：「深度重试」那一格不为零就说明补丁在干活；它恒为 0 而「页面没捕获」
照旧居高不下，就说明补丁没生效（注册失败的话活动日志里有一条 error）。
细节与代价见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 16、19、20 节。

### 兜底代理

轮询节点全试过还是失败时，可以再重发一次 —— 这一次走一个**你自己指定的 HTTP/HTTPS
正向代理**。填法和节点一样，就是「地址:端口」：

```
10.0.0.3:37581
http://10.0.0.3:37581
https://用户:密码@proxy.lan:8443
```

它**独立于节点列表**：不参与轮询、不测速、也不会被自动禁用 —— 最后一道防线不该自我禁用。
用自建的、经过时间验证的稳定代理最合适。

> **它是按「图源」生效的，不是按单张图。** 浏览器只把「协议 + 域名」交给分流脚本，
> 同一个源的两次请求在它眼里一模一样，所以「只让这一张图换代理」表达不出来。
> 兜底触发后的 **12 秒内**，这个图源的所有请求都会走兜底代理（包括本来正常的那些）；
> 随后进入 **30 秒冷却期**，冷却期内用尽的图直接裂掉。冷却是刻意的 —— 否则轮询池持续
> 失败时整个图源会长期只走兜底代理那一个 IP，而这正是本扩展存在意义的反面。

> **别填 `?url=` 那种模板。** 1.4.x 的兜底是「按地址取图的服务」（wsrv.nl 之类），
> 1.5.0 起换成了正向代理，两者协议不同、不能互换。填错的话输入框下方会当场说明原因，
> 开关也不会保持开启。
>
> 兜底代理和轮询池里任何一个节点一样看得到这些请求 —— 区别只在于地址是你自己填的。
> 不启用（关掉开关或留空）时重试用尽即裂图，不会有任何额外的数据外发。

装上没装上，看统计页的「重试与兜底」卡：「兜底接管」是切过去的次数，「兜底成功率」是
切过去之后真的加载成功的比例，「冷却期跳过」是本该切、但图源刚用过而没切的次数。
细节与代价见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 18 节。

**测速原理**：测速时扩展会为目标节点临时注入一份「把测速地址钉到该节点」的分流脚本，
且不加直连兜底。所以测出来的是「浏览器经该代理到公网」的真实端到端延迟，和图片请求走的是
同一条通路；失败也是真失败，不会被静默直连掩盖。因为一份脚本只能定向一个节点，测速是
**逐个串行**的，节点多时会慢一些。测速期间会临时接管浏览器代理设置，测完自动恢复。

## 常见问题

**图片还是加载失败？**
按顺序查：① 总开关是否打开；② 有没有节点显示可用延迟；③ 统计里「按规则送去代理」是不是
非零、「规则命中但直连」是不是 0（用规则测试器验证规则）；④ 弹窗「最近活动」里有没有
`request` 记录。四项都正常但仍失败，多半是代理本身不支持到目标站的 `CONNECT`
（HTTPS 图片必须经 CONNECT 隧道）。

**统计说走了几百次代理，但代理服务商后台一点流量都没有？**
这是 1.2.0 及更早版本的缺陷，已修复。原因是浏览器只把「协议 + 域名 + 端口」交给分流脚本，
按扩展名匹配的规则（当时的默认预设）永远命中不了，于是全部请求直连；而统计当时按完整 URL
判断，误以为它们都走了代理。现在这两件事被分开计数：「命中规则」与「按规则送去代理」，
差值单列为「规则命中但直连」。升级后请把依赖扩展名或路径的规则改成「域名」类型。

**节点全被自动禁用了？**
说明它们都没通过测速。点「重置」可解除自动禁用；若确认代理本身可用，检查测速地址是否
被你的网络环境屏蔽，换一个（例如 `http://cp.cloudflare.com/generate_204`）。

**提示「代理设置被占用」？**
浏览器的代理设置是独占资源。请关闭其他代理类扩展（Proxy SwitchyOmega、各类机场客户端
扩展等）后重新打开总开关。企业策略强制代理时本扩展无法接管。

**测速报「不支持跨域」？**
你自定义的测速地址没有返回跨域响应头。换回默认地址即可。

**为什么有些图片还是走了同一个节点？**
浏览器会复用已建立的 HTTP/2 连接，同一批图片可能共享同一条到代理的连接。这是网络栈行为，
不是扩展缺陷。缓解办法：节点数 ≥ 4、「每几个请求换一次节点」保持为 1。详见
[docs/LIMITATIONS.md](docs/LIMITATIONS.md)。

**我加的 SOCKS5 / VLESS 节点为什么用不了？**
本程序仅支持 HTTP/HTTPS 代理。这些类型会被明确标注为「不支持」，且不会参与分流。
可点「清除不支持的节点」一键删除。原因见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md)。

**卸载后浏览器代理会不会残留？**
不会。扩展被卸载或禁用时，Chromium 会自动撤销它设置的代理。手动关闭总开关也会立即恢复直连。

**日志里出现 `'pacScript.data' supports only ASCII code`？**
这是旧版本的缺陷，已修复。`chrome.proxy` 只接受纯 ASCII 的分流脚本，出现一个非 ASCII 字节
就会**整体**拒绝注入 —— 而拒绝之后浏览器照旧直连、图片照样加载，所以症状是「扩展像是什么
都没做」。现在脚本里的注释全是英文、配置里的中文一律转义、域名自动转 Punycode，并在注入前
再断言一次。如果还能看到这条错误，请开 issue 并附上「诊断」里导出的配置。

## 权限说明

| 权限 | 为什么需要 |
|---|---|
| `proxy` | 注入 PAC 脚本实现分流。这是扩展唯一能让浏览器网络栈走不同代理的手段 |
| `storage` | 保存节点、规则与设置 |
| `alarms` | 定时测速（Service Worker 会休眠，必须用 alarms 唤醒） |
| `webRequest` | **只读观测**请求结果，用于状态页的日志、出口 IP 展示，以及判断一次失败是代理故障还是图源自己返回了 404 |
| `webRequestAuthProvider` | 自动应答代理认证，避免每张图都弹认证框 |
| `<all_urls>` | 你可能给任意漫画站配规则，无法预先枚举域名 |
| 内容脚本（`content_scripts`） | 重试必须由页面里的代码执行 —— 扩展没有任何 API 能拦下一个正在失败的请求并改写它的代理。脚本跑在隔离世界，只监听图片加载失败、问后台该怎么办、按回复重新给 `<img>` 赋值；不读页面内容、不发网络请求、不碰 cookie、不修改页面全局对象 |
| `scripting` | 只用于「深度重试站点」：按你填的清单动态注册/注销那两个脚本。**清单为空时一个脚本都不会注册**，这个权限等于闲置 |

扩展不上传任何数据，配置与统计只存在本机 `chrome.storage.local`。
代理账号密码**不会**写入 PAC 脚本（PAC 语法不支持凭据），只在浏览器要求认证时按需提供。

**两个例外，都默认关闭：**

1. **兜底代理** —— 启用之后，重试全部失败的图源会在一段短窗口内改走你填的那个代理，
   于是它看得到这些请求（和轮询池里的节点一样）。窗口按「源」生效，会把同一图源当时
   其他正常的请求一起带上，详见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 18 节。
2. **深度重试站点** —— 填进去的站点会被注入**主世界**代码（改写页面自己的 `fetch` /
   `XHR` / `Image`）。这是本扩展做过的侵入性最强的事，所以必须逐个站点填，没有「全部
   开启」这个选项。那个站点因此也能借这条通道探测某个地址是否命中你的规则、或把统计
   计数刷高 —— 它拿不到节点、凭据或任何配置内容。详见
   [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 20 节。

不填就永远不会有额外的数据外发，也不会有任何主世界注入。

## 开发

```bash
npm test      # 运行全部 592 个测试（node --test，零依赖）
npm run check # 静态校验：manifest 引用、ESM 路径、命名导入、消息契约、架构约束
npm run icons # 重新生成图标 PNG
npm run verify # 上面两项一起跑
npm run pack  # 打包成 dist/image-proxy-rotator-<版本>.zip（分发 / 上架用）
npm run release # verify + pack
```

**目录结构**

```
manifest.json          MV3 清单
src/lib/               纯逻辑，零浏览器依赖，100% 单测覆盖
src/background/        Service Worker：只做 Chrome API 编排
src/content/           内容脚本：图片加载失败时换个代理重发（classic script，不能有 import）
src/pages/             设置页与状态弹窗
tools/                 图标生成、静态校验
tests/                 node:test 测试（单元 / 集成 / 后台编排 / SW 冒烟 / UI 契约）
docs/                  架构说明、技术限制、打包发布、人工验收清单
```

**架构约束**：`src/lib/` 下不得出现 `chrome.*` —— 这样 PAC 生成、节点解析、规则匹配、
调度这些最易错的部分可以在 Node 里直接 TDD，而不用靠人肉点浏览器。`npm run check` 会强制这条规则。

`src/background/` 虽然必须用 `chrome.*`，但同样有测试覆盖：`tests/helpers/chrome-stub.js`
提供 `chrome.*` 与 `fetch` 的替身，测试会把注入的 PAC 原文取出来在沙箱里执行，
用来验证「测速失败 → 自动禁用 → 重新注入的 PAC 不再选中该节点」这类跨模块行为。

细节见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)；打包与自动构建见 [docs/PACKAGING.md](docs/PACKAGING.md)。

自动化测试跑不到的部分（真实代理连通性、多个真实出口 IP、代理认证框、控制权争夺等）
整理成了 [docs/VERIFICATION.md](docs/VERIFICATION.md)，需要在浏览器里人工走一遍。

**开发者调试日志**（设置页 →「诊断」→「开发者调试日志」）

排查「为什么这张图没走代理 / 为什么没重试」时用它。打开开关 → 重现一次问题 → 回来导出。
导出的是纯文本，每个环节一个文件：

```
ipr-debug-pac-20260823-1420.log       PAC 编译出了什么、注入成没成
ipr-debug-request-…                    每个请求的 URL、状态码、对端 IP、归因结果
ipr-debug-retry-…                      重试判定的全部入参与结论
ipr-debug-content-…                    页面侧到底重发了没有、最后是 load 还是 error
ipr-debug-all-…                        全部合并，跨环节的时间线只有它连得起来
```

它与弹窗里的「最近活动」是两路独立的日志，互不影响。**默认关闭，关着时不产生任何开销**；
开启后记录在会话存储里，关掉开关或重启浏览器都会清空。

两件必须知道的事：导出的文件含你访问过的图片地址与代理服务器地址（不含代理账号密码），
贴到公开 issue 前请自己过一眼；另外**分流脚本内部的选路记不到** —— 它跑在浏览器的 PAC
沙箱里没有回传通道，「这个请求选了哪个节点」只能看 `request` 里的对端 IP
（见 [docs/LIMITATIONS.md](docs/LIMITATIONS.md) 第 21 节）。
